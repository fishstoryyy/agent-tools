This is a dedicated review pass that judges whether a piece of user-authored prompt or skill text will land naturally on a Codex agent, grounded in how Codex actually works — never in general intuition about "what agents like."

**Ground rules.** Ground every judgment in Codex source: quote the exact lines and file paths that justify each claim. "Fine as-is" is a first-class verdict; do not manufacture criticism to seem thorough, and flag only issues that could change agent behavior. Suggestions are withdrawable: when a new fact emerges mid-review (delivery channel, invocation mode, active model), re-evaluate earlier suggestions under it and explicitly retire any that no longer hold. If the Codex repo is unavailable, say so, judge from documented conventions only, and mark those claims as inference.

**0. Frame.** Before judging anything, establish the deployment frame. Identify the model, reasoning effort (`model_reasoning_effort`), and personality the user actually runs — ask, or read `~/.codex/config.toml`. Then resolve the prompt set that model runs: its entry in the model catalog (per-model instructions, `instructions_variables`, and `model_messages` tool-description overrides), its instruction template, and its base prompt. Run every check below against that prompt set, not the newest one. Model identity is load-bearing; reasoning effort is a strictness dial, not a frame — under low effort, ambiguous wording resolves to the cheapest reading, so explicit mechanism pins carry more weight. If the model is not in the local catalog, ask the user for its prompt file or mark frame claims as inference.

**1. Channel.** Determine where the text physically lands before judging voice. An explicitly invoked skill body arrives as a user-role message wrapped in `<skill>` tags; AGENTS.md and repo guidance arrive as developer-channel instructions; tool descriptions and system templates are product-authored and speak in second person. Voice must match channel: the developer channel natively says "you" to the agent; user-channel text naturally uses neutral third person or "us." Never recommend developer-channel voice for user-channel text.

**2. Referents.** Check that "agent," "user," "you," and "us" bind correctly. The active model's base prompt binds the frame in its opening line (for example, "You are Codex, a coding agent… You and the user share the same workspace…"). Any later "the agent" resolves to the addressee unless the context is a guardian or multi-agent prompt, where "agent" can denote others. If the reviewed text cannot arrive in such a frame, treat "the agent" as unambiguous self-reference.

**3. Mechanism.** Check whether the wording pins the behavior it wants. Codex often has two idiomatic mechanisms for one verb; the critical case is "asking the user," which is both blocking (ask, end the turn — ending the turn is the wait) and async (fire questions, keep working, proceed with the recommended option if unanswered). Wording like "ask before doing the task" is satisfied by both. If the user's intent needs a specific mechanism, flag the fork and propose an explicit pin, e.g. "Ask your questions and end your turn. Do not begin the underlying task until the interview has concluded." Phrase gates for iterated processes as "until … has concluded," not "until the user has answered" — one round is not concluded. Verify against the tool descriptions the active model actually sees, including any per-model overrides.

**4. Conventions.** Check for collisions with codified repo guidance: persistent-mode instructions, base prompts, mode templates, and tool specs. If Codex already dictates a default (for example, "if unanswered, proceed with the recommended option"), check whether the reviewed wording accidentally invokes it or silently fights it.

**5. Register.** Prefer vocabulary the source itself uses: pass, turn, final answer, underlying task, sandbox, approval, steer. Flag community jargon the source never uses. Do not flag correct, spec-like third person in skill preambles — that is the right register for a playbook handed to the agent.
**Locating the source.** Never assume the Codex repo is already available. Resolve it in order: if the current workspace is a codex checkout (a `codex-rs/` directory, or a git remote pointing at `openai/codex`), ground against it in place; otherwise ask the user for a checkout path; if they have none and consent, shallow-clone `openai/codex` into a cache directory and note the pinned ref; otherwise proceed in inference mode. Prefer a checkout close to the Codex version the user actually runs, and state which ref you grounded against — findings from a mismatched ref are approximate.

**Where to look.** Inside the resolved checkout, read `references/codex-source-map.md` for the map of prompt files, templates, model catalog, tool handlers, and skill-injection mechanics in the codex-rs repo, plus the drift caveats that come with it.

**Output.** Verdict up front: fine as-is / fine with one pin / needs rewording. Then the channel and frame actually established, in one line, with evidence. Then findings — only for checks that produced a flag or a confirmed-OK worth stating — each with the source lines that justify it. When suggesting wording, rank alternatives for the specific channel, and say which you would withdraw if the channel were different.
